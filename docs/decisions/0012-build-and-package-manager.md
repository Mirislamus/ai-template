# ADR 0012: Пакетный менеджер, сборка, анализ бандла и окружение

## Контекст и цели

Скорость сборки, стабильность зависимостей и предсказуемость рантайма на разных платформах (Windows, macOS, Linux/CI) определяют эффективность разработки.
Цели архитектурного стандарта:
1. **Единый пакетный менеджер:** использование Bun (`bun install`, `bun run`) с категорическим запретом смешивания с npm/yarn/pnpm.
2. **Бюджет производительности (Bundle Budget):** жесткие, но реалистичные лимиты на размер клиентского JS и CSS для стабильных метрик Lighthouse (пороги — [docs/quality.md](../quality.md) §2).
3. **Визуализация и контроль бандла:** интеграция интерактивного отчета `build:analyze` для выявления тяжелых зависимостей.
4. **Кроссплатформенность:** независимость команд `package.json` от операционной системы и оболочки (Windows PowerShell / Unix zsh).
5. **Фиксация требований к среде:** секция `engines` и обязательный шаблон `.env.example`.

---

## Принятые стандарты

### 1. Пакетный менеджер: Bun

- **Единый стандарт:**
  - Все операции по управлению пакетами (`bun add`, `bun remove`) и запуску скриптов (`bun run dev`, `bun run build`) выполняются **строго через Bun**.
- **Категорический запрет смешивания:**
  - Запрещено запускать `npm`, `yarn` или `pnpm`.
  - В `package.json` фиксируется поле `"packageManager": "bun@<версия>"` — фактическая версия из `bun --version` на момент инициализации проекта.
  - В репозитории коммитится только один lockfile — `bun.lock`. Файлы `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml` запрещены.
- **CI/CD пайплайны:**
  - На серверах интеграции используется официальный экшен `oven-sh/setup-bun@v2` с автоматическим кешированием зависимостей.

---

### 2. Бюджет производительности и лимиты чанков (Bundle Budget)

Для обеспечения мгновенной загрузки на мобильных сетях (Core Web Vitals) фиксируются следующие пороги:

1. **Критический первый экран (Hero / Above the fold JS):**
   - В профиле Astro: **0 Кб** клиентского JS по умолчанию (чистый `.astro`). До **25–30 Кб** gzipped при наличии критического интерактива в Hero.
   - В профиле Next.js: до **80–90 Кб** gzipped (базовый рантайм React Server Components).
2. **Отдельный клиентский чанк / интерактивный остров (Lazy chunk):**
   - Лимит: **до 70–80 Кб** gzipped (достаточно для формы с Zod, маской `imask` и иконками; исключает тяжелые библиотеки).
3. **Суммарный объем CSS на страницу:**
   - До **50 Кб** gzipped.
4. **Порог предупреждения сборщика (Vite):**
   - В конфиге сборщика задается `chunkSizeWarningLimit: 250` (Кб до сжатия). Превышение расценивается как архитектурный дефект.

---

### 3. Анализ состава бандла: `build:analyze`

- **Интерактивная карта модулей (Treemap):**
  - В Astro/Vite: плагин `rollup-plugin-visualizer`.
  - В Next.js: `@next/bundle-analyzer`.
- **Скрипт в `package.json`:**
  - Команда `"build:analyze"` (`ANALYZE=true astro build` или `ANALYZE=true next build`) собирает проект и генерирует наглядный HTML-отчет (`stats.html`), показывающий точный вклад каждой библиотеки в килобайтах.
- **Изоляция артефактов:**
  - Файлы отчетов `stats.html` и `.next/analyze/` обязательно занесены в `.gitignore`.

---

### 4. Кроссплатформенность и изоляция окружения

- **Запрет платформо-зависимого синтаксиса:**
  - Запрещены шелл-команды Unix (`export FOO=bar`, `rm -rf`, `cp -r`) внутри скриптов `package.json`.
  - Переменные окружения в скриптах задаются записью `VAR=value команда`: `bun run` выполняет скрипты в кроссплатформенной оболочке Bun, поэтому отдельный `cross-env` не нужен.
  - Для удаления директорий используются кроссплатформенные команды рантайма.
- **Требования к окружению (`engines`):**
  - В `package.json` строго фиксируются поддерживаемые версии:
    ```json
    {
      "engines": {
        "node": ">=24.0.0",
        "bun": ">=<версия на момент инициализации>"
      }
    }
    ```
- **Шаблоны конфигурации (`.env.example`):**
  - В корне репозитория обязателен файл `.env.example` со всеми переменными и комментариями к ним, но без реальных приватных ключей.
