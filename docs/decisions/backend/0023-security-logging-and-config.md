# ADR 0023: Безопасность API, конфигурация, логирование и файлы

## Контекст и цели

API принимает данные из интернета, хранит персональные данные и секреты интеграций. Ошибка в любой из этих зон приводит к утечке или простою.
Цели архитектурного стандарта:
1. **Недоверие к входу:** каждый запрос проверяется схемой, каждый ответ ограничен схемой.
2. **Защита от массовых атак:** лимиты запросов на уровне Nginx и приложения.
3. **Секреты вне кода:** конфигурация проверяется при старте, секреты не попадают в Git, логи и ответы.
4. **Наблюдаемость без утечек:** структурированные логи с `requestId`, без персональных данных; алерты о сбоях.
5. **Безопасные загрузки:** файлы пользователей проверяются по содержимому и отдаются только тем, кому они доступны.

---

## Принятые стандарты

### 1. Валидация входа и ответов

- Каждый маршрут объявляет Zod-схемы `body`, `query` и `params` из `model.ts` ([ADR 0019](0019-backend-architecture.md) §3). Неизвестные поля тела отбрасываются схемой.
- Каждый маршрут объявляет схему `response` ([ADR 0020](0020-api-contract-and-errors.md) §3): наружу не уходят поля, которых в ней нет.
- `GET` не меняет состояние. Изменения идут через `POST`, `PATCH`, `DELETE`.

### 2. Типовые атаки

- **SQL-инъекции:** только конструктор Drizzle и шаблон `sql` с параметрами ([ADR 0021](0021-database-and-migrations.md) §3).
- **CSRF:** API на том же домене, cookie сессии с `SameSite=Lax`, Better Auth проверяет `Origin` запросов к `/api/auth/*`. Мутации через `GET` запрещены (§1).
- **CORS** не включается ([ADR 0020](0020-api-contract-and-errors.md) §1).
- **Заголовки безопасности** выставляет Nginx ([ADR 0018](../common/0018-deployment-and-caching.md) §3).
- **Размер тела запроса** ограничивается в Nginx (`client_max_body_size`): 1 МБ для API, отдельный лимит для маршрутов загрузки файлов (§7).
- **Доступ к чужим данным (IDOR):** проверка владельца в запросе ([ADR 0022](0022-auth-and-access.md) §5).

### 3. Ограничение частоты запросов

- **Nginx:** общий лимит на `/api/` по IP (`limit_req`, 10 запросов в секунду с запасом 20, ответ `429`), конфиг — [ADR 0018](../common/0018-deployment-and-caching.md) §5.
- **Better Auth:** встроенные лимиты входа и регистрации ([ADR 0022](0022-auth-and-access.md) §7).
- **Формы и SMS:** модуль `src/shared/rate-limit.ts` — фиксированное окно в памяти процесса по ключу «IP + маршрут» (для SMS — дополнительно по номеру телефона). Превышение — `429 RATE_LIMITED`. При нескольких экземплярах API счетчики переносятся в PostgreSQL.
- **IP клиента** берется из заголовка `X-Real-IP`, который выставляет Nginx. Заголовку можно доверять, потому что порт API открыт только на `127.0.0.1` (§8).

### 4. Конфигурация и секреты

- **Проверка при старте:** `src/config/env.ts` разбирает `process.env` Zod-схемой и экспортирует типизированный объект `env`. При отсутствии или неверном формате переменной процесс падает при запуске с понятной ошибкой. Эталон — [docs/setup/backend.md](../../setup/backend.md).
- Прямое чтение `process.env` вне `env.ts` запрещено (как на фронтенде, [ADR 0004](../common/0004-ts-js-standards.md) §13). Исключение — конфиги инструментов (`drizzle.config.ts`).
- **Продакшен:** секреты лежат в файле `.env` на сервере рядом с `docker-compose.yml`, права `600`, владелец — пользователь деплоя. В Git попадает только `.env.example` с именами переменных.
- **CI:** секреты деплоя хранятся в GitHub Secrets.
- У каждого окружения (локальное, staging, продакшен) свои значения секретов. Утекший секрет немедленно заменяется.
- Случайные секреты генерируются командой `openssl rand -base64 32`.

### 5. Логирование

- **pino** пишет JSON в stdout. Обязательные поля записи о запросе: `requestId`, `method`, `path`, `status`, `durationMs`; для авторизованного запроса — `userId` (только идентификатор).
- **`requestId`:** Nginx передает `X-Request-Id: $request_id`; локально идентификатор генерируется. Значение возвращается в заголовке ответа и в теле ошибки ([ADR 0020](0020-api-contract-and-errors.md) §5):
  ```ts
  // apps/api/src/shared/request-id.ts
  const ids = new WeakMap<Request, string>();
  const REQUEST_ID_PATTERN = /^[\w-]{1,64}$/;

  export function getRequestId(request: Request): string {
    let id = ids.get(request);
    if (!id) {
      const header = request.headers.get('x-request-id');
      // Значение из заголовка проверяется, чтобы в лог не попадали произвольные строки
      id = header && REQUEST_ID_PATTERN.test(header) ? header : crypto.randomUUID();
      ids.set(request, id);
    }
    return id;
  }
  ```
- **Запрещено логировать:** тела запросов и ответов, пароли, коды подтверждения, токены, cookie, заголовок `Authorization`, телефоны, email, содержимое форм. Опция `redact` pino закрывает эти поля, даже если они случайно попали в объект лога.
- **Уровни:** `info` в продакшене, `debug` локально (`LOG_LEVEL`).
- **Хранение:** Docker пишет логи контейнеров в journald хоста; срок хранения — 14 дней (`MaxRetentionSec=14day` и ограничение объема `SystemMaxUse` в `/etc/systemd/journald.conf`), конфиг — [docs/setup/backend.md](../../setup/backend.md).

### 6. Мониторинг и алерты

- **Алерты в Telegram:** ошибки `500` и задачи очереди в статусе `failed` ([ADR 0019](0019-backend-architecture.md) §5) отправляются коротким сообщением в служебный чат через модуль `src/shared/alert.ts` (`ALERT_TELEGRAM_BOT_TOKEN`, `ALERT_TELEGRAM_CHAT_ID`).
- Сообщение содержит окружение, `code`, маршрут и `requestId`; персональные данные в него не входят.
- Одинаковый алерт (тот же маршрут и `code`) отправляется не чаще раза в 5 минут. Сбой отправки алерта пишется в лог и не прерывает обработку запроса.
- **Доступность:** внешний uptime-монитор раз в минуту проверяет `GET /api/health` ([ADR 0019](0019-backend-architecture.md) §6).
- Внешние трекеры ошибок (Sentry и аналоги) не подключаются без отдельного решения.

### 7. Файлы пользователей

- **Хранение:** каталог на диске сервера (`/srv/<project>/uploads`), смонтированный в контейнер API; путь внутри контейнера — `UPLOADS_DIR`. Подкаталоги `public/` и `private/`.
- **Доступ только через модуль** `src/shared/storage.ts` (`save`, `get`, `remove`). Остальной код не работает с файловой системой напрямую, поэтому переход на S3-хранилище изменит один модуль.
- **Проверки при загрузке:**
  - тип определяется по содержимому файла пакетом `file-type`, а не по расширению и не по `Content-Type` клиента;
  - разрешены только типы из списка проекта (по умолчанию JPEG, PNG, WebP, PDF); SVG и HTML запрещены (выполнение скриптов);
  - размер ограничен (по умолчанию 5 МБ) и в Nginx, и в схеме маршрута;
  - имя файла на диске — случайный UUID с расширением по определенному типу; исходное имя хранится только в БД.
- **Метаданные** (владелец, путь, тип, размер, исходное имя, видимость) хранятся в таблице `files`.
- **Публичные файлы** (`public/`) Nginx отдает напрямую с заголовком `X-Content-Type-Options: nosniff`.
- **Приватные файлы** (`private/`) отдаются после проверки прав в API: маршрут проверяет владельца ([ADR 0022](0022-auth-and-access.md) §5) и отвечает заголовком `X-Accel-Redirect`, а файл отдает Nginx из `internal`-location ([ADR 0018](../common/0018-deployment-and-caching.md) §5). Прямого адреса приватного файла нет.
- Каталог загрузок входит в ежедневный бэкап ([ADR 0021](0021-database-and-migrations.md) §6).

### 8. Зависимости и контейнеры

- `bun audit --audit-level=high` выполняется в CI на каждый PR; найденная уязвимость блокирует слияние ([ADR 0018](../common/0018-deployment-and-caching.md) §4).
- Dependabot раз в неделю предлагает обновления пакетов Bun и Docker-образов отдельными PR ([поддерживаемые экосистемы](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)). Обновления сливаются после зеленого CI.
- Процессы в контейнерах работают от непривилегированного пользователя (`USER bun`).
- Порт PostgreSQL не публикуется; порт API публикуется только на `127.0.0.1`, снаружи API доступен только через Nginx.
