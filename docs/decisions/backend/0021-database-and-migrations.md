# ADR 0021: База данных, Drizzle ORM, миграции и резервные копии

## Контекст и цели

Данные — самая дорогая часть проекта: ошибку в коде можно откатить, а потерянные или испорченные данные — нет.
Цели архитектурного стандарта:
1. **Единые соглашения схемы:** предсказуемые имена, ключи, даты и деньги во всех таблицах.
2. **Типобезопасные запросы:** Drizzle ORM без ручной склейки SQL-строк.
3. **Контролируемые миграции:** каждое изменение схемы — проверяемый SQL-файл в Git, применяемый отдельным шагом деплоя.
4. **Защита персональных данных:** реальное удаление по умолчанию.
5. **Восстановимость:** ежедневные резервные копии и регулярная проверка восстановления.

---

## Принятые стандарты

### 1. СУБД и подключение

- **PostgreSQL 18** (актуальная стабильная мажорная версия на момент принятия решения; в ней есть встроенная функция `uuidv7()`). Новый проект стартует на актуальной стабильной мажорной версии ([ADR 0010](../common/0010-third-party-libraries-policy.md) §1).
- **Drizzle ORM** через встроенный драйвер Bun SQL (`drizzle-orm/bun-sql`, [документация](https://orm.drizzle.team/docs/connect-bun-sql)). Подключение создается один раз в `src/db/client.ts` ([docs/setup/backend.md](../../setup/backend.md)).
- Приложение подключается к БД отдельной ролью без прав суперпользователя — владельцем своей базы. Роль из `POSTGRES_USER` официального образа является суперпользователем и используется только для обслуживания (бэкапы, восстановление); роль приложения создается init-скриптом ([docs/setup/backend.md](../../setup/backend.md) §7).
- Порт PostgreSQL наружу сервера не публикуется ([ADR 0018](../common/0018-deployment-and-caching.md) §5).

### 2. Соглашения схемы

- **Имена:** таблицы во множественном числе, таблицы и колонки в snake_case в БД (`order_items.created_at`), поля в TypeScript в camelCase. Перевод выполняет опция `casing: 'snake_case'` Drizzle и drizzle-kit.
- **Первичный ключ:** `id uuid primary key default uuidv7()`. UUIDv7 не позволяет перебирать соседние записи и оценивать объемы бизнеса по номерам, при этом сортируется по времени создания.
- **Служебные колонки каждой таблицы:** `created_at timestamptz not null default now()` и `updated_at timestamptz not null default now()`; `updated_at` обновляется через `$onUpdate`.
- **Даты:** только `timestamptz`; хранение и обмен в UTC ([ADR 0020](0020-api-contract-and-errors.md) §3).
- **Деньги:** целое число в минимальных единицах валюты (`bigint`, для UZS — тийины) и колонка `currency char(3)` с кодом ISO 4217. Типы `real`, `double precision` и `numeric` для денег не используются.
- **Статусы:** колонка `text` с `check`-ограничением и union-типом в TypeScript. `pgEnum` не используется: удаление и переименование его значений требует пересоздания типа.
- **Внешние ключи** объявляются всегда, с явным `onDelete` (`cascade`, `restrict` или `set null`). Колонки внешних ключей и частых фильтров индексируются.
- **Таблицы Better Auth** (`user`, `session`, `account`, `verification`) генерируются командой `bunx auth@latest generate` в `src/db/schema/auth.ts` и в дальнейшем меняются только через нее ([ADR 0022](0022-auth-and-access.md) §1). Формат их идентификаторов задает Better Auth.
- Пример таблицы проекта:
  ```ts
  // apps/api/src/db/schema/orders.ts
  import { sql } from 'drizzle-orm';
  import { bigint, char, check, pgTable, text, timestamp, uuid } from 'drizzle-orm/pg-core';

  import { user } from './auth';

  export const orders = pgTable(
    'orders',
    {
      id: uuid().primaryKey().default(sql`uuidv7()`),
      userId: text().notNull().references(() => user.id, { onDelete: 'cascade' }),
      status: text().$type<'new' | 'paid' | 'cancelled'>().notNull().default('new'),
      amount: bigint({ mode: 'number' }).notNull(),
      currency: char({ length: 3 }).notNull(),
      createdAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
      updatedAt: timestamp({ withTimezone: true }).notNull().defaultNow().$onUpdate(() => new Date()),
    },
    table => [check('orders_status_check', sql`${table.status} in ('new', 'paid', 'cancelled')`)],
  );
  ```

### 3. Запросы и транзакции

- Запросы строятся конструктором Drizzle. Сырой SQL допускается только через шаблон ``sql`...` `` с подстановкой параметров; склейка SQL из строк запрещена (SQL-инъекции).
- Запись в несколько таблиц выполняется в `db.transaction()`. Постановка фоновой задачи идет в той же транзакции, что и бизнес-запись ([ADR 0019](0019-backend-architecture.md) §5).
- Выборка ресурса пользователя всегда содержит условие владельца в `where` ([ADR 0022](0022-auth-and-access.md) §5).

### 4. Удаление данных

- **По умолчанию удаление реальное** (`DELETE`): по запросу пользователя его персональные данные должны исчезнуть из базы.
- **Мягкое удаление** (`deleted_at timestamptz`) вводится только для конкретной таблицы по явному решению, когда нужна корзина или история. Каждый запрос к такой таблице фильтрует `deleted_at is null`.
- Персональные данные удаленного пользователя не остаются в мягко удаленных строках: они удаляются или обезличиваются.

### 5. Миграции

- **Создание:** `bun run db:generate` (`drizzle-kit generate`) создает SQL-файл в `apps/api/drizzle/`. Файл проверяется на ревью и коммитится вместе с изменением схемы.
- **Применение:** `bun run db:migrate` (скрипт `src/db/migrate.ts` с мигратором `drizzle-orm/bun-sql/migrator`) запускается отдельным шагом деплоя до переключения на новую версию API ([ADR 0018](../common/0018-deployment-and-caching.md) §5). Если миграция упала, деплой останавливается и продолжает работать старая версия. API при старте миграции не применяет.
- `drizzle-kit push` разрешен только для локальной базы разработчика.
- Примененная миграция не редактируется: исправление — новой миграцией.
- **Разрушающие изменения** (удаление или переименование колонки, смена типа) делаются в два релиза: сначала добавляется новое и код переходит на него, следующим релизом удаляется старое. Так старая версия API продолжает работать, пока применяется миграция.
- CI проверяет, что миграции не забыты: `drizzle-kit generate` на чистом checkout не должен создавать новых файлов ([ADR 0018](../common/0018-deployment-and-caching.md) §4).
- Тестовые данные для локальной разработки создаются скриптом `src/db/seed.ts`; на проде он не запускается.

### 6. Резервные копии

- **Ежедневно** по cron на хосте выполняется `pg_dump -Fc` базы и архивирование каталога загруженных файлов ([ADR 0023](0023-security-logging-and-config.md) §7) в `/var/backups/<project>/`. Файлы доступны только root (`chmod 600`).
- **Срок хранения** — 14 дней, более старые копии удаляются тем же скриптом.
- **Раз в месяц** последняя копия восстанавливается во временную базу (`pg_restore`) и проверяется запросом к ключевым таблицам; результат записывается в [STATE.md](../../../STATE.md).
- **Известный риск:** копии хранятся на том же сервере, что и база. При выходе сервера из строя или его взломе база и копии теряются одновременно. Устранение — добавить в скрипт бэкапа отправку копий на отдельный сервер (например, restic по SFTP); остальная схема не меняется.
