# ADR 0019: Архитектура бэкенда, модули и фоновые задачи

## Контекст и цели

Лендингу с формой заявки достаточно эндпоинта Astro ([ADR 0001](../frontend/0001-project-architecture.md) §7). Проектам со своей базой данных, личным кабинетом, админкой или фоновыми задачами нужен отдельный API.
Цели архитектурного стандарта:
1. **Бэкенд по необходимости:** отдельный API подключается только по явному решению в [PRODUCT.md](../../../PRODUCT.md).
2. **Единый стек:** Bun, Elysia, TypeScript strict ([ADR 0004](../common/0004-ts-js-standards.md)), Zod, Drizzle ORM, PostgreSQL.
3. **Монорепо со сквозными типами:** фронтенд и бэкенд в одном репозитории, типы API доходят до клиента без ручного дублирования.
4. **Модули по фичам:** код одной фичи лежит в одной папке, слои внутри модуля не смешиваются.
5. **Надежные фоновые задачи:** отправка заявок во внешние сервисы не теряется при их недоступности и не требует новых сервисов инфраструктуры.

---

## Принятые стандарты

### 1. Когда подключается бэкенд

- Бэкенд подключается, если проекту нужно хотя бы одно из перечисленного: собственная база данных, авторизация пользователей, админка, фоновые задачи или API для нескольких клиентов.
- Прием формы с отправкой в Telegram или CRM без хранения данных реализуется эндпоинтом Astro или Route Handler Next.js; отдельный бэкенд для этого не создается.
- Решение фиксируется в [PRODUCT.md](../../../PRODUCT.md) по итогам допроса ([PROMPT.md](../../../PROMPT.md)).

### 2. Монорепо на Bun workspaces

Проект с бэкендом организуется как монорепо; дерево папок — [ARCHITECTURE.md](../../../ARCHITECTURE.md), эталонные конфиги — [docs/setup/common.md](../../setup/common.md).

- `apps/web` — фронтенд (Astro или Next.js), правила [docs/decisions/frontend/](../frontend/).
- `apps/api` — бэкенд на Elysia.
- `packages/shared` — общие Zod-схемы, типы и константы. Пакет не зависит от фреймворков и не содержит обращений к БД, сети и окружению.
- **Направление зависимостей:**
  - `apps/web` импортирует из `apps/api` только тип приложения: `import type { App } from 'api'` (ADR 0020 §1). Рантайм-код бэкенда в клиентский бандл не попадает.
  - `apps/api` не импортирует `apps/web`.
  - Оба приложения могут импортировать `packages/shared`.

### 3. Модули по фичам

Код бэкенда раскладывается по модулям `apps/api/src/modules/<feature>/` (структура, рекомендованная Elysia: [Best Practice](https://elysiajs.com/essential/best-practice)):

| Файл | Ответственность | Запрещено |
|---|---|---|
| `index.ts` | Маршруты Elysia: схемы запроса и ответа из `model.ts`, проверка доступа (ADR 0022), вызов сервиса | Запросы к БД, бизнес-логика |
| `service.ts` | Бизнес-логика и запросы Drizzle | Зависимость от `Context` Elysia: сервис получает обычные аргументы (`userId`, `input`) |
| `model.ts` | Zod-схемы тела, параметров и ответа | Логика и побочные эффекты |
| `*.test.ts` | Тесты модуля рядом с кодом ([ADR 0014](../common/0014-testing-and-qa.md) §6) | — |

- Отдельный слой репозиториев не создается: при тестах на реальной БД ([ADR 0014](../common/0014-testing-and-qa.md) §6) он не нужен для подмены, а лишний файл в каждом модуле усложняет код.
- Таблицы Drizzle объявляются в `src/db/schema/` (один файл на сущность), а не в модулях: на таблицу обычно ссылаются несколько модулей.
- **Импорты внутри `apps/api`** идут через subpath imports `#src/*` из `package.json` (`import { db } from '#src/db/client'`), а не через алиас `@/*` из `tsconfig.json` ([ADR 0001](../frontend/0001-project-architecture.md) §3). Фронтенд проверяет типы файлов API со своими настройками, и алиас `@/*` указал бы на `apps/web/src`; subpath imports привязаны к пакету. Эталон — [docs/setup/backend.md](../../setup/backend.md) §1.
- **Связи между модулями:** сервис может вызывать экспортированную функцию сервиса другого модуля. Импорт маршрутов (`index.ts`) другого модуля и циклические зависимости запрещены. Общий код без бизнес-специфики выносится в `src/shared/`.

### 4. Адреса API

- Все маршруты собираются под префиксом `/api` (Elysia `prefix`), Nginx проксирует этот путь на API ([ADR 0018](../common/0018-deployment-and-caching.md) §5).
- Версия в адресе (`/api/v1`) не используется: фронтенд и бэкенд деплоятся вместе, несовместимость типов видна при сборке через Eden (ADR 0020).
- Версионирование вводится отдельным ADR, когда у API появляются внешние клиенты (мобильное приложение, партнеры).

### 5. Фоновые задачи: очередь в PostgreSQL (outbox)

- **Постановка задачи:** сервис записывает бизнес-данные и задачу в таблицу `jobs` в одной транзакции. Если транзакция откатилась, задачи нет; если зафиксировалась, задача не потеряется.
- **Таблица `jobs`:** `id`, `type`, `payload` (`jsonb`), `status` (`pending`, `processing`, `done`, `failed`), `attempts`, `run_at`, `last_error`, `created_at`, `updated_at`.
- **Worker** — отдельный процесс из того же образа (`src/worker.ts`), отдельный контейнер в Docker Compose ([docs/setup/backend.md](../../setup/backend.md)):
  - выбирает пачку готовых задач запросом с блокировкой `FOR UPDATE SKIP LOCKED`, поэтому несколько экземпляров worker не берут одну задачу дважды;
  - при ошибке увеличивает `attempts` и переносит `run_at` с экспоненциальной задержкой; после 5 неудачных попыток ставит `failed` и отправляет алерт (ADR 0023 §6);
  - обработчики задач лежат в `src/jobs/` и идемпотентны: повторное выполнение не создает дублей во внешней системе.
- Redis и брокеры сообщений не используются без отдельного решения.

### 6. Запуск, остановка и здоровье процесса

- `src/index.ts` запускает HTTP-сервер, `src/app.ts` собирает приложение Elysia и экспортирует `type App`.
- Маршрут `GET /api/health` проверяет соединение с БД (`select 1`) и отвечает `200` или `503`. Он используется healthcheck Docker и внешним uptime-мониторингом (ADR 0023 §6).
- По сигналу `SIGTERM` API и worker перестают принимать новую работу, завершают текущие запросы и задачи и закрывают соединение с БД.
