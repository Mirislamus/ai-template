# ADR 0014: Стратегия тестирования, автоматизация проверок и критерии приемки

## Контекст и цели

Надежность веб-сайта складывается из выявления ошибок на ранних стадиях без замедления процесса разработки.
Цели архитектурного стандарта:
1. **Прагматичная пирамида тестирования:** 70% статический анализ (TypeScript, ESLint, Stylelint, W3C HTML), 20% Unit-тесты логики и схем (Vitest), 10% E2E Smoke-тесты (Playwright).
2. **Валидация синтаксиса W3C HTML:** автоматическая проверка `html-validate` сгенерированной разметки в `dist/`.
3. **Быстрое модульное тестирование:** использование **Vitest** с окружением `happy-dom` для проверки схем Zod и чистых утилит.
4. **Безопасные Smoke-тесты:** изоляция сетевых запросов в **Playwright** через мокирование (`page.route`) для исключения тестового спама в CRM.
5. **Контроль консоли браузера:** автоматическое падение тестов при наличии необработанных ошибок JavaScript.
6. **Жесткий Definition of Done:** чеклист из 6 объективных критериев готовности к релизу в продакшен, включая пост-деплой валидацию в браузере.

## Принятые стандарты

### 1. Пирамида тестирования для веб-сайтов

Распределение усилий строится по принципу максимальной отдачи:

1. **Статический анализ и W3C валидация (Фундамент — 70% покрытия рисков):**
   - Строгий TypeScript (`strict: true`), ESLint (`--max-warnings 0`), Stylelint.
   - **W3C HTML Validation (`html-validate`):** автоматическая проверка синтаксиса собранной разметки в `dist/` командой `bun run validate:html` (запрет незакрытых тегов, дублирования `id`, невалидной вложенности).
2. **Модульные тесты (Unit & Logic — 20%):**
   - Инструмент: **Vitest**.
   - **Обязательно покрывается тестами:**
     - Схемы валидации Zod (`*.schema.test.ts`) — граничные значения полей, очистка телефонов, email.
     - Чистые вычислительные утилиты (расчеты цен, скидок, форматирование валют, дат).
     - Мапперы и трансформации данных API.
   - **Не покрываются:** простые статичные UI-компоненты разметки без бизнес-логики.
3. **Сквозные Smoke-тесты (E2E — 10%):**
   - Инструмент: **Playwright**.
   - Проверка только критического пользовательского пути (Happy Path):
     - Открытие ключевых страниц с HTTP-статусом 200.
     - Работоспособность мобильного бургер-меню.
     - Заполнение и отправка формы заявки.
     - Отсутствие необработанных ошибок в консоли браузера.

---

### 2. Инфраструктура Vitest

- **Конфигурация:**
  - Использование тестового окружения `happy-dom` (высокая скорость эмуляции DOM).
  - Поддержка алиасов `@/*` из `tsconfig.json`.
- **Размещение тестов:**
  - Тестовые файлы располагаются строго рядом с тестируемым кодом:
    - `src/features/contact-form/model/contact-form.schema.test.ts`
    - `src/shared/lib/format-currency.test.ts`
- **Скрипты запуска:**
  - `"test"`: `vitest run` — однократный прогон всех тестов для проверок и CI.
  - `"test:watch"`: `vitest` — интерактивный режим разработки с перезапуском по сохранению.

---

### 3. Сквозные тесты: Playwright Smoke-tests

- **Размещение:** `tests/e2e/` (например, `tests/e2e/smoke.spec.ts`).
- **Обязательное мокирование сети (`page.route`):**
  - Все сетевые запросы форм к внешним API эмулируются:
    ```ts
    await page.route('**/api/contact', async route => {
      await route.fulfill({ status: 200, json: { success: true } });
    });
    ```
  - Это защищает от отправки тестового мусора в рабочие Telegram-каналы и CRM-системы.
- **Мульти-вьюпорт:**
  - Тесты запускаются минимум в двух профилях: Desktop (1280×720) и Mobile (390×844) для контроля тач-событий и адаптива.
- **Защита от тихих ошибок консоли:**
  - Ошибки собираются в массив, а проверка выполняется в конце сценария (падение внутри обработчика события не завершает тест надежно):
    ```ts
    const errors: string[] = [];
    page.on('pageerror', error => errors.push(error.message));
    page.on('console', message => {
      if (message.type() === 'error') errors.push(message.text());
    });

    // ... сценарий проверки страницы ...

    expect(errors).toEqual([]);
    ```

### 4. Критерии приемки и готовности к релизу (Definition of Done)

Проект считается готовым к деплою в продакшен **только** при одновременном выполнении следующих критериев:

1. **Статический анализ и синтаксис (Code Quality Gate):**
   - Команда `bun run check` (`format:check`, `lint`, `typecheck`) завершается с кодом 0 и нулевым количеством предупреждений.
   - `bun run validate:html` проходит с 0 ошибок.
2. **Автотесты (Tests Passed):**
   - Модульные тесты Vitest (`bun run test`) и E2E smoke-тесты Playwright (`bun run test:e2e`) пройдены.
   - В проекте с бэкендом пройдены тесты `apps/api` (§6), и `drizzle-kit generate` не создает новых миграций ([ADR 0021](../backend/0021-database-and-migrations.md) §5).
3. **Чистая сборка в рамках бюджета (Build Success):**
   - Команда `bun run build` завершается без ошибок.
   - Размеры чанков и CSS укладываются в бюджет производительности ([ADR 0012](0012-build-and-package-manager.md)).
4. **Метрики качества:**
   - Пороги Lighthouse и Core Web Vitals (в том числе `CLS = 0`) — единый источник [docs/quality.md](../../quality.md) §2.
5. **Визуальный smoke-контроль:**
   - Проверены 5 состояний форм (включая ошибки валидации и отправки).
   - Проверена адаптивность на узких экранах (360–390 px): горизонтальной прокрутки (`overflow-x`) нет.
6. **Пост-деплой верификация в браузере (Production Check):**
   - После деплоя на боевой домен проверяются ключевые страницы:
     - **Google Rich Results Test:** зеленый статус для типов, которые поддерживает Google (хлебные крошки, `Product`, `Organization` / `LocalBusiness`; см. [ADR 0013](../frontend/0013-seo-standards.md) §4).
     - **Schema.org Validator:** 0 ошибок в графе JSON-LD (включая `FAQPage`).
     - **W3C Nu HTML Checker:** 0 ошибок синтаксиса разметки.

### 5. Мониторинг ошибок в продакшене и клиентское логирование

- **Прагматичный двухуровневый подход:**
  1. **Стандартные сайты и лендинги (по умолчанию):**
     - Внешние тяжелые трекеры не подключаются (0 Кб лишнего веса).
     - Достаточно локального `ErrorBoundary` на клиенте для предотвращения белого экрана + серверного логирования ошибок API-запросов.
  2. **Крупные сервисы и личные кабинеты (Next.js / Enterprise):**
     - Подключается легковесный клиент Sentry или GlitchTip.
- **Фильтрация шума браузерных расширений:**
  - Игнорируются сторонние ошибки: `ResizeObserver loop limit exceeded`, ошибки расширений (`chrome-extension://`), сетевые отмены `AbortError`.
- **Строгая маскировка персональных данных (PII):**
  - Категорически запрещено отправлять в логи пароли, телефоны, email или вводимый текст из полей форм. Все чувствительные поля заменяются на `[REDACTED]`.
- Логи и алерты отдельного бэкенда — [ADR 0023](../backend/0023-security-logging-and-config.md) §5–6.

### 6. Тесты бэкенда (`apps/api`)

- **Инструмент:** встроенный раннер `bun test`. Фронтенд остается на Vitest (§2).
- **Реальная база:** тесты работают с отдельной тестовой базой PostgreSQL в Docker (сервис `db-test` в `compose.dev.yml`, [docs/setup/backend.md](../../setup/backend.md)). Перед прогоном применяются миграции; моки базы данных не используются, потому что не ловят ошибки SQL и миграций.
- **Изоляция:** каждый тестовый файл очищает свои таблицы перед запуском (`TRUNCATE ... CASCADE`); тесты не зависят от порядка выполнения.
- **Запросы без сервера:** маршруты проверяются через `app.handle(new Request(...))`, без запуска HTTP-сервера.
- **Внешние сервисы** (Telegram, SMS, CRM, почта) в тестах не вызываются: обработчики задач получают подменные функции отправки.
- **Размещение:** `src/modules/<feature>/<feature>.test.ts` рядом с кодом модуля.
- **Обязательные тесты каждого защищенного маршрута:**
  1. без сессии — `401 UNAUTHORIZED`;
  2. без нужной роли или подтверждения — `403` ([ADR 0022](../backend/0022-auth-and-access.md) §4–5);
  3. чужой ресурс — `404 NOT_FOUND` ([ADR 0022](../backend/0022-auth-and-access.md) §5);
  4. невалидные данные — `422 VALIDATION_FAILED`;
  5. успешный сценарий — ожидаемый статус и тело по схеме ответа.
- **Логика сервисов** (расчеты, переходы статусов, очередь задач) покрывается тестами сервиса напрямую, без HTTP.
