# ADR 0001: Архитектура проекта, профили стека и организация кода

## Контекст и цели

Веб-проекты имеют разные требования к нагрузке, индексации и динамике: от сверхбыстрых промо-лендингов с нулевым JavaScript до сложных интерактивных сервисов с авторизацией и панелями управления.
Цели архитектурного стандарта:
1. **Четкое разделение профилей:** однозначный выбор между Astro (SSG/Islands) и Next.js (App Router/SSR) на старте проекта без избыточного оверхеда.
2. **Масштабируемость без бюрократии:** применение адаптированной трехуровневой методологии FSD-Lite для чистоты модулей и строгого направления зависимостей.
3. **Стандартизация путей:** единый чистый корневой алиас `@/*` (`src/*`) и запрет относительных подъемов `../../../`.
4. **Контроль гидратации:** градуальная загрузка клиентского интерактива в Astro Islands и вынесение Client Components на листья дерева в Next.js.
5. **Гибридный рендеринг в Next.js:** грамотное сочетание статики (SSG), фонового обновления (ISR) и серверного динамического рендера (SSR).
6. **Типобезопасный контент:** использование Astro Content Collections с проверкой схем через Zod без сторонних баз данных.

---

## Принятые стандарты

### 1. Выбор профиля проекта (Astro vs Next.js)

- **Профиль Astro (SSG / Islands) — стандарт по умолчанию:**
  - **Область применения:** промо-лендинги, корпоративные сайты, каталоги услуг и товаров, блоги, контентные многостраничники.
  - **Приоритеты:** скорость загрузки (Lighthouse 100/100, Core Web Vitals), 0 Кб клиентского JS на первом экране, генерация чистой статики.
  - **Интерактив:** точечные интерактивные острова на React через директивы гидратации.
- **Профиль Next.js (App Router) — специализированный профиль:**
  - **Область применения:** веб-сервисы, личные кабинеты (авторизация, сессии), дашборды, сложные серверные мутации данных (Server Actions), API Route Handlers.
  - **Запрет:** запрещено выбирать Next.js для классических лендингов ради удобства разработчика (оверхед гидратации и размер бандла снижают оценки Core Web Vitals).

### 2. Структура кодовой базы: FSD-Lite

Кодовая база в `src/` организуется по облегченной трехуровневой модели:

```text
src/
├── shared/          # Базис: переиспользуемые UI-компоненты, утилиты, типы, стили, env
│   ├── ui/          # Кнопки, инпуты, модалки, спиннеры
│   ├── styles/      # Глобальные токены, миксины, переменные
│   ├── config/      # Конфигурация окружения (env.ts)
│   ├── utils/       # Чистые вспомогательные функции
│   └── types/       # Общие типы данных
├── features/        # Законченные интерактивные сценарии (бизнес-модули)
│   ├── lead-form/   # Форма заявки (валидация, маска, отправка)
│   ├── theme-toggle/# Переключатель темы
│   └── catalog-filter/ # Фильтрация каталога
├── widgets/         # Крупные композиционные секции страниц
│   ├── header/      # Шапка сайта с навигацией
│   ├── footer/      # Подвал сайта
│   ├── hero/        # Первый экран
│   └── faq/         # Секция часто задаваемых вопросов
├── layouts/         # Каркасы страниц (BaseLayout.astro / RootLayout.tsx)
├── content/         # Astro Content Collections (статьи, услуги, кейсы)
└── pages/ (или app/)# Маршруты страниц фреймворка
```

#### Правило направления зависимостей:
- Импорты идут строго снизу вверх: `pages` → `widgets` → `features` → `shared`.
- **Запрет горизонтальных связей:** модули одного слоя (например, `features/lead-form` и `features/theme-toggle`) не могут импортировать друг друга напрямую. Взаимодействие происходит через слой выше (`widgets` или `pages`) либо через глобальные атомы/сторы в `shared`.

### 3. Конвенция путей и алиасов

- **Единый корневой алиас `@/*`:**
  - В `tsconfig.json` настраивается ровно один алиас на папку `src/`:
    ```json
    {
      "compilerOptions": {
        "baseUrl": ".",
        "paths": {
          "@/*": ["src/*"]
        }
      }
    }
    ```
- **Относительные импорты (`./`):** разрешены строго внутри локальной директории одного компонента/модуля (например, импорт стилей `./Button.module.scss` или типов `./Button.types`).
- **Запрет многоуровневых подъемов:** пути вида `../../../shared/ui/button` категорически запрещены. Использовать: `@/shared/ui/button/Button`.

### 4. Стратегия гидратации в профиле Astro (Islands)

- **Разметка по умолчанию:** пишется строго в компонентах `.astro` (0 Кб JavaScript в браузере).
- **Выбор директивы гидратации для React Islands:**
  1. **`client:load` (Критический интерактив первого экрана):** разрешен строго для интерактивных элементов в зоне видимости первого экрана (Hero), требующих мгновенного отклика (например, калькулятор на первом экране). Запрещен для блоков ниже сгиба.
  2. **`client:visible` (Стандарт по умолчанию):** применяется для всех интерактивных блоков ниже первого экрана (слайдеры, формы, отзывы, аккордеоны). Загружает и инициализирует JS только при приближении к области видимости экрана.
  3. **`client:idle` (Фоновые виджеты):** применяется для некритичных элементов, подгружаемых после завершения основной загрузки страницы (чаты поддержки, виджеты обратного звонка).
  4. **`client:media="(max-width: 768px)"`:** для адаптивных элементов, физически существующих только на мобильных устройствах (мобильное меню-шторка).
  5. **`client:only="react"`:** запрещен без технического согласования (выключает SSR и вредит SEO).

### 5. Стратегия рендеринга в профиле Next.js (SSG / ISR / SSR)

Компоненты и страницы разделяются по строгой матрице рендеринга:

1. **SSG (Static Site Generation) — стандарт по умолчанию:**
   - Статичные информационные страницы («О компании», контакты, правовая информация, лендинги).
   - Собираются в момент билда и моментально отдаются через CDN.
2. **ISR (Incremental Static Regeneration) — для периодически обновляемых данных:**
   - Страницы каталогов, блогов, прайс-листов, отзывов.
   - **Time-based:** фоновая перегенерация через интервал времени:
     ```tsx
     export const revalidate = 3600; // обновление раз в час
     ```
   - **On-demand:** мгновенная ревалидация по тегу или пути при сохранении данных в админке через Server Actions:
     ```tsx
     revalidateTag('catalog-products');
     revalidatePath('/blog');
     ```
   - Генерация статических параметров для динамических роутов:
     ```tsx
     export async function generateStaticParams() {
       const items = await getCatalogSlugs();
       return items.map(item => ({ slug: item.slug }));
     }
     ```
3. **SSR (Server-Side Rendering / Dynamic) — строго по необходимости:**
   - Персонализированные страницы, личные кабинеты, корзина, оформление заказа, чтение cookies/headers.
   - Включается через `export const dynamic = 'force-dynamic'` или обращение к `cookies()`.
4. **Правило Server vs Client Components (RSC):**
   - Все страницы, секции и макеты — строго Server Components (без `'use client'`).
   - Директива `'use client'` спускается на самые мелкие «листья» дерева (кнопка счетчика, интерактивный фильтр, форма).

### 6. Управление контентом: Astro Content Collections

- **File-based контент со строгими схемами:**
  - Все контентные сущности (статьи, услуги, тарифы, кейсы) хранятся в `src/content/` в форматах `.md`, `.mdx` или `.json`.
  - Каждая коллекция обязана иметь строгую схему валидации в `src/content/config.ts` через встроенный Zod:
    ```ts
    import { defineCollection, z } from 'astro:content';

    const services = defineCollection({
      type: 'content',
      schema: z.object({
        title: z.string(),
        description: z.string(),
        price: z.number().positive(),
        isFeatured: z.boolean().default(false),
        publishedAt: z.date(),
      }),
    });

    export const collections = { services };
    ```
- **Отказ от лишних баз данных:** Content Collections исключают потребность в отдельных БД для типичных сайтов и лендингов, обеспечивая проверку типов во время сборки.
- **Внешняя CMS:** подключение сторонней Headless CMS (Strapi, Directus) допускается только при явном требовании клиента предоставить визуальную панель управления для контент-менеджеров.
